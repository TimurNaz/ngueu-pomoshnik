# Обзор архитектуры НГУЭУ/Помощник

## Что сделано хорошо

1. **Чёткое разделение на сервисы** — бот, API, фронтенд и БД живут в отдельных контейнерах, общаются через Docker-сеть.

2. **Продуманная модель данных** — 9 таблиц, 10 enum-ов, реферальная система, бонусы, лояльность, оплата. Для MVP это сильная база.

3. **Telegram-интеграция** — Mini App открывается из бота, `initData` передаётся для аутентификации, haptic feedback, expand/close — всё по гайдлайнам Telegram.

4. **Nginx как reverse proxy** — фронтенд проксирует `/api/` и `/static/` на FastAPI, SPA-роутинг через `try_files`.

5. **Дизайн-система на CSS Variables** — BEM-нейминг, токены цветов/радиусов/теней. Аккуратный подход без фреймворков.

6. **Документация** — структурированная `/docs` с INDEX, метаданными, разделением по доменам.

## Архитектурные проблемы

### 1. Связанность API и бота (самая серьёзная)

```python
# backend/api/main.py
from backend.bot.main import bot  # ← прямой импорт
```

API напрямую импортирует экземпляр бота для отправки уведомлений админу:
- API не может работать без бота
- Невозможно масштабировать их независимо
- Риск circular import

**Решение**: очередь сообщений (Redis pub/sub, или общая таблица `notifications` в БД, которую бот читает по крону).

### 2. Авторизация — проверка подписи без проверки идентичности

`check_tg_auth` проверяет валидность подписи Telegram, но не сверяет `user_id` из подписи с `user_id` из запроса. Любой аутентифицированный пользователь может:

```
GET /api/orders/client/ЧУЖОЙ_USER_ID       ← чужие заказы
POST /api/orders { client_id: ЧУЖОЙ_USER_ID }  ← заказ от чужого имени
```

**Решение**: извлекать `user.id` из `initData` и сверять с параметрами запроса.

### 3. MemoryStorage в боте

```python
dp = Dispatcher(storage=MemoryStorage())
```

FSM-состояния (например, согласие на обработку данных) теряются при рестарте бота. Пользователь застрянет посередине флоу.

**Решение**: `RedisStorage` (код уже закомментирован в `main.py`). Добавить Redis-сервис в docker-compose.

### 4. Enum mismatch (urgency)

Фронтенд шлёт `3d`, `1w`, `2w`, `1m`. БД ожидает `three_days`, `one_week`, `two_weeks`, `one_month`. В API есть маппинг-хак, но это хрупко.

**Решение**: привести к единому формату на стороне фронтенда или API.

### 5. Нет пагинации

```
GET /api/orders/client/{id}  → возвращает ВСЕ заказы
```

При росте числа заказов — OOM или долгий ответ.

**Решение**: добавить `?page=1&limit=20`.

### 6. Файлы на локальном диске

`/backend/static/uploads` монтируется как Docker-том:
- Не масштабируется на несколько серверов
- Нет автоматического бэкапа
- Нет CDN

**Решение**: Yandex Object Storage (S3-совместимый).

## Несоответствия в бизнес-логике

**Уровни лояльности** — документация и код расходятся:

| Источник | novice | 2-й уровень | 3-й уровень | 4-й уровень |
|----------|--------|-------------|-------------|-------------|
| Документация | 0–10k | bronze 10–30k | silver 30–70k | gold 70k+ |
| Код (models.py) | 0–3k | student 3–8k | regular 8–15k | vip 15k+ |

Кэшбэк начисляется только VIP (5%), но логика пересчёта при `order.status = done` не вызывается нигде.

## Итог

Для MVP/стартапа архитектура **хорошая**. Разделение на сервисы, продуманная модель данных, грамотный Telegram-сетап. Главные точки роста: развязать API от бота, закрыть дыру в авторизации и дореализовать бизнес-логику (оплата, кэшбэк, исполнители). Фундамент крепкий — на нём можно строить.
